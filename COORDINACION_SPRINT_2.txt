CONTRATO ACTUAL PARA EL FRONTEND
Peticion: GET /api/sitios
Respuesta HTTP 200:
{
  "sitios": [
    {"id":1,"estado":"libre","mensaje":"La plaza 1 esta disponible"},
    {"id":2,"estado":"ocupado","mensaje":"La plaza 2 no esta disponible"}
  ]
}
El servidor real devuelve el texto con tildes.
Estados admitidos: "libre" y "ocupado", siempre en minusculas.
id es un numero estable compartido por frontend, backend y simulador.
El frontend debe usar estado, no interpretar el texto de mensaje.
La respuesta sin plazas sera {"sitios":[]}.
Cualquier cambio de campos o tipos debe acordarse antes con el equipo.

COMO JUNTAR EL TRABAJO ESTE SPRINT
1. Todos parten de main actualizado y trabajan en su propia rama.
   Guardar los cambios propios antes de cambiar de rama.
   git switch main
   git pull --ff-only origin main
   git switch <rama-personal>
   git merge main
   Resolver los conflictos juntos si dos personas han editado el mismo archivo.
2. Instalar dependencias con npm ci y arrancar el backend con npm start.
3. Primera integracion: Pau consulta la API y muestra las dos plazas.
   Si frontend y backend usan puertos distintos, acordar un proxy de desarrollo
   o configurar CORS para el origen concreto. CORS no esta configurado ahora.
   localhost apunta al ordenador de cada uno: para probar entre portatiles,
   usar la IP del equipo que ejecuta el backend y comprobar la conexion de red.
4. Segunda integracion, si hay tiempo: Alex recibe el mensaje MQTT de Marc,
   actualiza el estado y la siguiente consulta de Pau refleja el cambio.
   GET /api/sitios solo consulta: publicar MQTT no cambiara los datos hasta
   que Alex implemente la suscripcion y la actualizacion.
   Para la primera demo basta volver a consultar; tiempo real con Socket.io
   puede quedar para una tarea posterior.
5. Comprobar tambien la consulta a la base de datos. Conectarla al flujo
   completo sera un paso adicional, no algo que ya haga esta API.
6. Antes de unir cada rama a main, revisar el cambio, ejecutar npm test
   y probarlo con los otros componentes. Usar una pull request para que
   otro companero pueda revisarlo. No reemplazar archivos de otros sin revisar.

CRITERIO PROPUESTO DE CIERRE
Minimo recomendable: backend y frontend conectados, simulador MQTT probado
por separado, prueba de conexion a la base de datos y evidencias claras de
lo que funciona y lo que queda pendiente.
Objetivo ampliado: simulador -> MQTT -> backend -> consulta de la API ->
frontend, con un cambio visible de libre a ocupado y de ocupado a libre.
Si no se llega, registrar el bloqueo y la tarea pendiente para el siguiente
sprint. No presentar datos fijos como una integracion MQTT funcional.
